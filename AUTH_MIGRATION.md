# Secure browser authentication — deployment and migration

Phase 2A.1 replaces the bundled shared bearer credential with one owner password and server-side sessions. Changes are local only: no deployment, production environment changes, credential rotation, database access, commits or pushes were performed.

## Authentication flow

- `GET /api/auth/session` initializes a 15-minute anonymous CSRF session or reports the current authenticated session. It returns `{ authenticated, csrfToken }`; the CSRF token stays in JavaScript memory.
- `POST /api/auth/login` accepts `{ password }`, an exact allowed `Origin`, and `X-CSRF-Token`. Node scrypt verifies the backend-only salted hash (N=32768, r=8, p=1, 64-byte key). Successful login regenerates the session ID and CSRF token.
- `POST /api/auth/logout` requires the same Origin/CSRF checks, invalidates the server session and expires the cookie.
- All other `/api` paths are behind the same default-deny authentication boundary. Session-authenticated POST/PUT/PATCH/DELETE requests require Origin and CSRF validation. There is no development authentication bypass.
- Production uses a host-only `__Host-workspace.sid` cookie: Secure, HttpOnly, SameSite=Lax, Path=/, persistent expiry. Explicit `NODE_ENV=development` uses an HTTP-compatible `workspace.sid` cookie for localhost only.
- Authenticated sessions expire absolutely after 7 days by default, with no sliding extension. Changing the password hash or signing secret invalidates existing sessions. A password change requires generating and configuring a new hash, not a public password-reset endpoint.
- Session files are separate from `db.json`, use hashed filenames, restricted file modes, atomic replacement and logout tombstones. Expired records are cleaned on subsequent session writes, at most once per 15 minutes. A store failure fails closed. No hosted database or paid provider is added.
- Login permits 10 attempts per 15 minutes globally; auth endpoints allow 60 requests per minute globally. This deliberately protects the single owner independently of proxy/IP spoofing. Counters live in memory, reset on restart, and a hostile client can temporarily exhaust the login budget. Keep one Node process and one Railway replica.
- The React gate mounts personal screens only after session verification. A 401 clears React Query data, aborts pending requests, rejects late responses and shows login. Logout removes persisted timer/focused-task details but keeps the selected view. Other open tabs receive a logout signal when BroadcastChannel is available; foreground verification is the fallback. Failed server logout hides data and offers Retry sign out; reconnect to finish invalidation before leaving the device.
- All `/api` responses, including auth/error responses, send browser and CDN `no-store` headers. The Phase 1 service worker still caches only static assets, excludes all API/auth routes and retains its Reload/Later update prompt. No offline data editing, sync or widget APIs were added.

## Railway variables

Do not put these in Vite variables or a client environment file.

| Name | Purpose / required action |
| --- | --- |
| `AUTH_PASSWORD_HASH` | Required. Salted scrypt hash from the setup script. |
| `SESSION_SECRET` | Required. At least 32 random bytes, hex encoded, generated by the setup script. Keep stable across normal deployments. |
| `NODE_ENV` | Use `production` on Railway. Only explicit `development` permits non-Secure localhost cookies. |
| `ALLOWED_ORIGINS` | Required in production: exact HTTPS frontend origins, comma separated, no wildcard, path or trailing slash. Include only deliberate preview origins while testing; remove them later. |
| `DATA_DIR` | Preserve the existing productivity data directory and mounted volume; do not move or change it for this migration. |
| `SESSION_DIR` | Optional if DATA_DIR is correct: defaults to `<DATA_DIR>/sessions`. Otherwise required in production. Must be a writable directory on the existing persistent volume, separate from the database file. |
| `SESSION_TTL_DAYS` | Optional, defaults to 7; allowed range 1–30. A new setting applies to new logins. |
| `TRUST_PROXY` | Set to a verified proxy hop count or exact trusted proxy IP/CIDR list. Unset trusts no proxy. Never use `true` or guess a hop count. Behind Railway HTTPS termination, verify this before testing cookies. |
| `LEGACY_AUTH_ENABLED` | Default off. Set exactly `true` only for the short migration window; set `false` to disable it. |
| `LEGACY_AUTH_EXPIRES_AT` | Required only when legacy is enabled: an ISO UTC deadline no more than 7 days ahead. Requests stop accepting the legacy token at this time without a restart. |
| `APP_TOKEN` | Retain the existing value only during the explicit migration window. Remove/revoke it after verification. |

Existing `PORT` and `ANTHROPIC_API_KEY` remain backend-only and unchanged. No new frontend environment variables are required. `VITE_API_URL` is intentionally no longer read: the new client always uses same-origin `/api`. Remove `VITE_APP_TOKEN` and `VITE_API_URL` from future frontend builds manually, after preserving the old deployment during migration.

Production startup validates authentication configuration before existing startup migrations/unpinning. **Starting the normal server still invokes the existing database startup behavior.** Tests and the browser fixture never run that entry point.

## Generate credentials privately on Windows

1. Run `npm ci` at the repository root.
2. In your own interactive terminal, run `npm run auth:setup -w server`.
3. Enter and confirm a strong unique password of at least 12 characters. Input is hidden, never passed as command arguments and never printed.
4. The script writes `server/auth-secrets.env` with the hash and a random signing secret. It refuses to overwrite an existing file. This filename is gitignored. Open it privately and copy each value into Railway's secret configuration; omit the surrounding dotenv quotes. Never paste values into chat, logs, screenshots, tickets or documentation.
5. Store the password in your password manager. Securely remove the local secret file when no longer needed. On Windows, file mode 0600 does not replace Windows ACLs: keep the file in a private account directory and do not sync/share it. No real credentials were generated as part of automated testing.

For isolated local development, explicitly use `NODE_ENV=development`, `ALLOWED_ORIGINS=http://localhost:5173`, a disposable `DATA_DIR`, and the generated backend settings. Vite continues proxying `/api` to localhost:3001. Do not point development or tests at the production volume. The existing root `.env` may specify production mode; choose the development values explicitly in your own environment. `DOTENV_CONFIG_PATH` can select the generated file if needed. Never reuse production credentials for local testing.

## Vercel rewrite and proxy verification

The repository does not identify the live Railway hostname, Vercel project root/settings, proxy topology or volume mount. **Do not deploy the new client until its `/api` proxy is configured and tested.** The checked-in `client/vercel.json` keeps the existing Phase 1 headers; no guessed upstream hostname has been inserted.

If Vercel's project Root Directory is `client`, add this top-level `rewrites` property to `client/vercel.json`, keeping its `headers` property. Replace the illustrative hostname with the verified public HTTPS Railway backend hostname:

```json
"rewrites": [
  {
    "source": "/api/:path*",
    "destination": "https://YOUR-VERIFIED-RAILWAY-HOST/api/:path*"
  }
]
```

If the project root is elsewhere, apply this to the configuration Vercel actually reads. Preserve query strings, HTTP methods/bodies, `Cookie`, `Set-Cookie`, `Origin`, and `X-CSRF-Token`; never inject an Authorization credential. Do not add redirects or a catch-all SPA rewrite ahead of `/api`. State-based app navigation still uses `/`.

Verify through the frontend HTTPS origin that:

- `/api/auth/session` returns JSON, not the frontend HTML, and sets the host-only cookie on the frontend domain.
- The cookie has Secure, HttpOnly, SameSite=Lax and Path=/, with no Railway Domain attribute.
- Login sends the frontend Origin unchanged, and the next request carries the cookie.
- API/auth responses have `Cache-Control: no-store`, are not served from the CDN/service worker cache and are not cached by any custom Vercel rule.
- Railway receives trusted HTTPS forwarding. Determine the actual proxy path, including direct-to-Railway requests as well as Vercel-to-Railway requests, and set `TRUST_PROXY` accordingly. The trusted edge must overwrite attacker-supplied forwarding headers. Do not blindly set a multi-hop count; shorter alternate paths can invalidate that assumption.

See [Vercel external rewrites](https://vercel.com/docs/routing/rewrites), [Express proxy trust](https://expressjs.com/en/guide/behind-proxies/), and [Express secure sessions](https://expressjs.com/en/resources/middleware/session/).

## Persistent volume

Keep the current Railway volume and `DATA_DIR` unchanged. Place session files in its `sessions` subdirectory (or an explicit SESSION_DIR on that same volume). Verify runtime permissions and persistence across a Railway restart/deploy. Never expose the session directory through static hosting, commit it or copy it into a frontend build. Restrict backup access as session data is sensitive.

This store is designed for the existing **one process, one replica, one persistent volume** application. It does not coordinate multiple workers or replicas. Do not enable clustering or scale replicas with this store. The existing JSON productivity database has the same single-writer constraint. Railway volume configuration must be verified in the dashboard; see [Railway volumes](https://docs.railway.com/volumes).

## Exact backend-first migration sequence

1. Record the known-good deployment versions and verify the existing backup procedure, volume mount, frontend origin and Railway URL. Do not run migrations, test writes or cleanup against real productivity data. Use a separate staging/disposable data directory for mutation tests.
2. Generate new backend-only credentials privately. Configure the required Railway variables above. Preserve DATA_DIR, current APP_TOKEN and Anthropic configuration. Temporarily enable legacy auth with a short UTC deadline (within 7 days). Both the flag and deadline are required; missing auth configuration fails startup.
3. Deploy **only the backend** first using the existing Railway build/start commands. Do not let an automatic simultaneous Vercel deployment publish the new client yet; pause/separate deployment triggers if necessary. No start command or hosting settings have been inferred or changed by this implementation.
4. Verify the existing frontend still reads data using the temporary legacy path. Check the new session endpoint through the intended same-origin rewrite. Confirm secure cookie/proxy behavior before proceeding. CORS must allow the exact old frontend origin if it still calls Railway directly.
5. Configure the verified Vercel rewrite. Remove the obsolete VITE_APP_TOKEN and VITE_API_URL settings from the new frontend build, rebuild, run the artifact check below, then deploy the new frontend. A preview origin must be explicitly allowed on the backend; restrict access to previews and remove temporary origins afterward.
6. Test desktop and iPhone as below while legacy support remains enabled. Verify session persistence across a Railway restart and verify logout invalidation. Use staging synthetic records for create/update/delete and AI request tests; this implementation's automated tests never call AI or production data APIs.
7. Set `LEGACY_AUTH_ENABLED=false` and redeploy/restart the backend. Confirm an old cached client (or an old bearer request without a session cookie) now receives 401, including on direct Railway API requests. New cookie-authenticated clients must still work. Removing APP_TOKEN alone is not the intended disable procedure while the legacy flag is true, because startup validation will reject that configuration.
8. Remove the exposed APP_TOKEN from Railway, remove LEGACY_AUTH_EXPIRES_AT, and remove old VITE_APP_TOKEN values from all Vercel environment scopes/local env files. The flag remains false/unset. If that token was reused anywhere else, rotate it there privately. Do not create a replacement frontend token. Restrict/remove old public build artifacts where practical: revocation, not artifact deletion, makes copies harmless.
9. Bring each installed PWA online, accept its existing Reload update prompt after saving work, and confirm it shows the new login. Old cached bundles may remain on devices but their bearer credential no longer grants access. Do not re-enable it to accommodate a stale PWA.

## Manual desktop and iPhone checks

1. In a clean desktop browser profile, open the HTTPS frontend. Confirm the login screen appears and private API requests without a session receive 401. Try an incorrect password, then the correct one. Confirm no Authorization header is sent by the new client.
2. Open tasks, notes, habits, grocery, sleep, settings and books. Confirm the existing views load. On staging only, create/update/delete a synthetic record and exercise an AI operation as appropriate.
3. Select a view and reload. Confirm the session and view remain. Close and reopen the browser within the configured session lifetime. Restart the backend and verify the same session survives with its persistent volume and unchanged credentials.
4. Sign out. Confirm personal screens disappear, a previous session cookie no longer authorizes requests, and reload remains signed out. Check another open tab and browser Back. For a failed/offline logout, verify the warning and complete Retry sign out after reconnecting.
5. In iPhone Safari, open the same HTTPS origin, sign in, then Share → Add to Home Screen → Add. Launch from the icon. Safari and an installed web app may use separate storage contexts: sign in in the installed app if prompted.
6. Confirm standalone display, notch/Home indicator spacing, password keyboard usability, scrolling and navigation. Close/reopen the installed app and verify login persistence. Sign out and sign back in from the installed app.
7. Test expiry using a disposable staging session (or revoke by changing staging credentials); the next request must show login without looping. API calls lacking CSRF or with an untrusted Origin must return 403.
8. Test a new frontend deployment: bring the installed app online, accept Reload, and verify the session survives. With legacy disabled, an old cached client must receive 401 until updated.

Physical iPhone Safari/PWA storage, keyboard/safe areas, HTTPS proxy forwarding, Vercel CDN behavior, real production volume persistence and production deployment settings cannot be confirmed by local Windows tests. They remain required manual checks.

## Automated checks and safe browser fixture

From the repository root:

```powershell
npm run test -w server
npm run test -w client
npm run build
node client/scripts/check-pwa.mjs
npm run check:auth -w client
npm audit --omit=dev
```

The backend tests start only a database-free Express app on loopback with temporary synthetic sessions and stub handlers for every mounted private API prefix. They never import `server/src/index.ts`, route implementations, dotenv, or the productivity database. They cover login failures/success, ID rotation, persistence, revocation, expiry, cookie flags, CSRF/Origin, legacy flags/deadline, global API protection and corrupt storage. Client tests exercise the existing API wrappers with mocked fetch, CSRF/cookie options, 401 handling, late responses and logout. Full business-route/database regression testing remains outside this auth-only change.

For an optional browser smoke test, after building, run `npx tsx server/tests/preview-auth.ts` in one terminal and `npm run preview -w client -- --host localhost --port 4173 --strictPort` in another. The fixture uses only the synthetic password declared in that test file and fake empty API responses. Do not use real credentials. Ensure port 3001 is available; it must not be a running real backend. Close both processes with Ctrl+C afterward. The fixture cleans only its verified temporary session directory.

The artifact checker scans all built frontend files for obsolete auth variable names and the known secret values available in backend/client local env files or its process environment. It prints no secret values or matching snippets. A pass proves those supplied values are absent; it cannot discover an unknown historical credential. Run in a trusted private environment containing the old token for comparison, never expose it through a new VITE variable. Inspect the actual deployed assets privately too; a local build check alone does not prove which version Vercel serves. Check source maps and historical public artifacts if any.

Local results: 8 backend tests and 4 client tests pass; production build, backend TypeScript (including setup/test helpers), git diff whitespace validation and PWA/artifact checks pass. Browser smoke testing against the synthetic fixture verified incorrect-password rejection, sign-in, Tasks navigation, authenticated reload/view restoration, sign-out and a signed-out reload. The build retains existing large-chunk and PostCSS module-type warnings. Targeted compatible lockfile patches update proxy-addr and ip-address, used by proxy trust/rate limiting. Existing moderate body-parser/qs advisories remain for a separate dependency-maintenance pass; this task does not broadly upgrade the application.

## Rollback and limitations

- Before legacy revocation, the old frontend can temporarily run against the new backend until the explicit deadline; keep the migration window short. Old and new clients should be tested separately so a session cookie does not mask a legacy test.
- After revocation, do not roll back to the old bearer frontend/backend or re-enable the exposed token. Roll forward with a session-capable fix. An old frontend cannot be made secure by merely rotating a token that it will embed again.
- Losing session files, rotating SESSION_SECRET or changing AUTH_PASSWORD_HASH forces re-login; it does not affect productivity records. Keep normal deploy secrets stable. Existing sessions retain their original expiry if only SESSION_TTL_DAYS changes.
- These changes do not encrypt the existing productivity data or session volume and do not repair unrelated JSON database behavior. HttpOnly mitigates cookie theft, but XSS can still act as the signed-in user. Use a unique password and a trusted device.
- No password recovery, multi-user accounts, widgets or backend widget tokens are introduced. Future Scriptable access must have its own scoped, revocable authentication design, independent of browser cookies.
